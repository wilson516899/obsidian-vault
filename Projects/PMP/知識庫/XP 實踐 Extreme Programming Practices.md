# XP 實踐 Extreme Programming Practices

> [[Projects/PMP/知識庫/_索引|← 知識庫索引]] ｜ `Governance 績效領域` › `Executing` › `Manage Project Execution`
> 屬於敏捷框架的工程實踐，見 [[Projects/PMP/知識庫/僕人式領導與敏捷角色|僕人式領導與敏捷角色]]（XP 的角色：Coach）

> [!tip] 一句話核心
> XP 的實踐分兩種：**跟客戶溝通、建立共同理解**的，跟**純技術內部品質**的。題目問「跟客戶建立共同願景」時，只有**面向客戶的那一個**是對的，其他都是真實存在但答錯問題的干擾項。

---

## XP 四大常考實踐，先分兩類

| 分類 | 實踐 | 面向誰 | 解決什麼問題 |
|---|---|---|---|
| **面向客戶／建立共同理解** | **User Stories 使用者故事** | **客戶 × 開發者** | 用雙方都懂的語言（「身為 X，我想要 Y，以便 Z」）描述需求，是**對話的起點**，不是規格書 |
| 技術／團隊內部工程實踐 | **Continuous Integration 持續整合** | 開發者之間 | 頻繁整合程式碼、自動測試，**及早抓到整合問題** |
| 技術／團隊內部工程實踐 | **Pair Programming 結對編程** | 開發者之間 | 兩人一機共同開發，**提升程式碼品質、知識共享** |
| 技術／團隊內部工程實踐 | **Test-Driven Development（TDD）先寫測試** | 開發者內部 | 先寫測試再寫程式，**驅動設計、確保品質** |

> 🔑 **只有 User Stories 直接連結客戶與開發者**——它是特意用「非技術語言」寫的，目的就是讓客戶看得懂、能參與對話。其他三個都是**開發團隊內部**的工程紀律，客戶通常不會、也不需要參與。

---

## 🎯 判準：題目問「跟客戶建立共同願景／共同理解」→ 永遠是 User Stories

| 錯誤選項 | 為什麼錯 |
|---|---|
| **Continuous Integration**（你選的） | 解決的是**程式碼整合品質**問題，是**技術**實踐，客戶完全不參與、也看不懂這在做什麼 |
| **Pair Programming** | 提升的是**開發團隊內部**的程式碼品質與知識傳遞，跟客戶無關 |
| **Test-Driven Development** | 驅動的是**技術設計與品質**，測試案例是給開發者看的，不是給客戶溝通用的 |

> 💡 這是敏捷考題常見的陷阱模式：**四個選項都是真的 XP 實踐**，但題目在問「哪一個的**目的**是連結客戶」，不是「哪一個是 XP 實踐」。要看**目的／面向對象**，不是看「聽起來像不像敏捷」。

---

## User Stories 的標準格式

> **As a** [使用者角色]**, I want** [目標]**, so that** [好處/理由]。
> 身為 [使用者角色]，我想要 [目標]，以便 [好處/理由]。

- 通常寫在**索引卡片**上，是**對話的佔位符（placeholder for a conversation）**，不是完整規格
- 聚焦在**使用者需求**，而非技術規格
- 讓客戶的觀點**貫穿整個開發決策**過程

## 🎯 情境應用：發佈流程要同時達成「更高品質＋更快部署」，四個聽起來都對的選項怎麼選

E068：行動應用程式發佈流程優化，目標是**同時**達成「更高品質」與「更快部署時間」。四個選項全部都是真實存在、合理的工程實務，差別在**誰能同時滿足這兩個目標**：

| 選項 | 為什麼不是最佳 |
|---|---|
| ✅ 在 CI/CD 流程中實施**自動**回歸測試，以便即時獲得程式碼變更的回饋 | 這是唯一**自動化、內建在流水線裡**的選項——每次程式碼變更都立刻有回饋，同時達成**品質**（及早攔截回歸問題）與**速度**（不用等人工驗證，部署可以持續往前推進） |
| 在每次合併前引入同儕審查流程，讓主程式碼庫能及早發現問題 | 能提升品質，但是**人工流程**——審查需要人力與時間排程，對「**更快部署**」反而可能是新的瓶頸，不是加速器 |
| 定期與外部顧問進行程式碼稽核，以確保遵循最佳實務 | **週期性、外部、非即時**——稽核排程是定期的（例如每季一次），既不是每次變更都檢查，也無法加快部署速度，跟「即時回饋、持續部署」的方向相反 |
| 增加程式碼整合的頻率，以鼓勵較小且易於管理的更新（你選的） | 只處理了「**批次大小**」這個面向（變更變小、較好管理），但本身**不包含任何自動驗證機制**——沒有自動化回饋，光是整合更頻繁，不保證品質更高，也不必然讓部署更快 |

> 🔑 判準：題目要求**同時**達成「品質」與「速度」兩個目標時，先問哪個選項是**自動化且內建在流程裡**的——人工流程（同儕審查）、週期性外部流程（顧問稽核）、只調整批次大小但沒有驗證機制（增加整合頻率）都只能單獨解決其中一半，只有**自動化測試＋即時回饋**能同時滿足兩者。

## 🎯 情境應用：連續好幾個 Sprint 交付物都沒達到客戶品質期望，怎麼選「提升未來 Sprint 品質」的行動

E069：敏捷專案已經**連續多個 Sprint**交付物未達客戶品質期望，導致客戶不滿。題目問：要提升**未來 Sprint** 的交付品質，該採取什麼行動？四個選項同樣全部都是合理的工程／流程做法：

| 選項 | 為什麼不是最佳 |
|---|---|
| ✅ 引入同儕審查與配對程式設計，以提升程式碼品質，然後再進行客戶審查 | 這是**在交到客戶手上之前**，多一層「人」去對照需求與邏輯做檢查——能攔截的是**自動化測試抓不到**的落差（例如：技術上沒 bug，但沒做到客戶真正要的東西），直接對應題目講的「**客戶**品質期望沒被滿足」這個落差 |
| 實施自動化測試以進行持續整合，確保錯誤能被及時發現並修正 | 能抓**技術性的 bug／回歸問題**，但題目講的落差是「沒達到**客戶**的品質期望」——這通常不只是程式有沒有 bug，更可能是**理解或執行上跟客戶要的不一樣**，自動化測試對這類落差的覆蓋有限 |
| 為開發團隊舉辦全面的敏捷與品質最佳實務培訓課程 | **太籠統、太慢見效**——「全面培訓」解決的是普遍性的知識缺口，但題目描述的是**具體、重複發生**的交付品質落差，培訓不是針對這個具體落差的直接介入 |
| 與團隊重新評估並精煉「完成」的定義，確保其中包含嚴格的品質標準（你選的） | **只是把標準寫得更嚴格，沒有提供達到這個標準的機制**——問題已經**重複發生好幾個 Sprint**，代表團隊不是「不知道要做到什麼程度」，而是**過程中沒有機制攔截落差**。重新定義 DoD 設了更高的門檻，但沒有解決「怎麼確保做得到」這件事 |

> 🔑 判準：題目描述**已經重複發生、具體的交付品質落差**（不是「不知道標準」，而是「標準有了也做不到」）時，優先選**能在過程中實際攔截落差的機制**（同儕審查／配對程式設計這種「多一雙眼睛對照需求」的做法），而不是「把標準寫得更嚴格」（DoD 精煉）或「普遍性補強」（培訓）或「只抓技術性 bug」（自動化測試）——這四個選項分別對應**人工交叉檢查、標準制定、知識補強、技術偵測**四種不同性質的介入，題目給的訊號決定哪一種才對症。

---

## 判斷口訣

> 題目問「**跟客戶建立共同願景／共同理解／溝通需求**」→ **User Stories**。
> 題目問「**程式碼品質、整合、測試**」這類**純技術**目的 → CI／Pair Programming／TDD，但這些**不涉及客戶**。
> 四個選項都是真的 XP 實踐時，先看**面向對象是客戶還是開發團隊內部**，再選。
