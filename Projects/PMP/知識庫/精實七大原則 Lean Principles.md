# 精實七大原則 Lean Principles

> [[Projects/PMP/知識庫/_索引|← 知識庫索引]] ｜ `Governance 績效領域` › `Executing` › `Manage Project Execution`
> 屬於敏捷／精實思維，常與 Agile Practice Guide 一起考

> [!tip] 一句話核心
> **先辨認症狀屬於哪一種「浪費」，再對應到該用哪條精實原則——這題四個選項全部都是真的精實原則，考的是誰對症。**

---

## 七大原則（Poppendieck）

| 原則       | 英文                                 | 核心動作                               |
| -------- | ---------------------------------- | ---------------------------------- |
| **消除浪費** | Eliminate Waste                    | **找出並移除**不創造價值的活動（等待、多餘審批、過度文件、返工） |
| 增強學習     | Amplify Learning                   | 用短迭代、快速回饋加速學習                      |
| 儘量延遲決策   | Defer Commitment                   | 保留彈性，等資訊夠了再做**不可逆**的決定             |
| 儘快交付     | Deliver Fast                       | 縮短交付週期，小批量、高頻率交付                   |
| 賦權團隊     | Empower the Team                   | 讓最了解狀況的人做決定，而非由上而下指揮               |
| 內建誠信／品質  | Build Integrity In                 | 品質從一開始就內建進流程，而非事後檢驗補救              |
| 全局最佳化    | See the Whole / Optimize the Whole | 看整個價值流，避免各部門各自優化造成整體變差             |

---

## 🎯 本題判準：症狀本身就是「浪費」的定義，直接對應「消除浪費」

題目描述的三個症狀，全部都是精實框架裡**明確命名的浪費類型**：

| 題目症狀 | 對應的浪費類型 |
|---|---|
| 「必須經過**多個審批階段**」 | **交接／過度處理**（Handoffs／Over-processing） |
| 「編碼前需要**大量文件**」 | **過度處理**（Over-processing——做了超過需求的工作） |
| 「等**數天**才能得到專家答覆」 | **等待**（Waiting——這是最經典的浪費類型之一） |

> 🔑 判準：當題目描述的症狀**可以逐一對應到具體的浪費類型**（等待、過度處理、交接、返工…）時 → 直接選 **Eliminate Waste**，因為這些症狀本身就是「浪費」的教科書定義。

---

## ⚠️ 為什麼另外三個選項是錯的（本題）

| 錯誤選項                      | 為什麼錯                                                                                     |
| ------------------------- | ---------------------------------------------------------------------------------------- |
| **Deliver Fast 儘快交付**     | 這是**結果／目標**（縮短週期時間），不是**診斷症狀該對應的原則**。本題症狀是「為什麼慢」，不是「怎麼樣才能快」——先移除浪費，交付自然變快，兩者是因果關係，不能倒果為因 |
| **Build Quality In 內建品質** | 題目沒有出現**品質缺陷、事後補救、測試不足**的訊號，純粹是**流程冗長與等待**，跟品質無關                                         |
| **Defer Commitment 延遲決策** | 這是關於**何時做出不可逆決定**的原則，題目沒有出現「太早鎖定方案」這類情境，訊號不對                                             |

> 💡 這四個選項都是**真實存在**的精實原則，不是三個假的干擾項——這種題型考的不是「你知不知道這個原則」，是「**你能不能把症狀對應到正確的原則**」。

## 🧮 軟體開發的七種浪費（多選題常考，本題形式）

> 上面的「消除浪費」原則，具體展開就是這七種**明確命名**的浪費類型（Poppendieck 對應到軟體開發）：

| 浪費類型     | 英文                  | 例子                                            |
| -------- | ------------------- | --------------------------------------------- |
| 部分完成的工作  | Partially Done Work | 寫到一半的程式碼、還沒測試的功能                              |
| **多餘功能** | Extra Features      | **做了客戶要求、但實際很少用的功能**——這是「多做了」的浪費，不是「做錯了」      |
| 重複學習     | Relearning          | 團隊一再重新摸索已經解決過的問題（知識沒留存）                       |
| 交接       | Handoffs            | 工作在人／團隊間轉手，每次轉手都遺失資訊、增加延誤                     |
| 任務切換     | Task Switching      | 一心多用、頻繁被打斷，切換成本本身就是浪費                         |
| **延遲**   | Delays              | **等待別人回覆、等待審批**——最直覺的浪費類型                     |
| **缺陷**   | Defects             | **因誤解需求而返工**、抓 bug、修補——缺陷本身、以及缺陷造成的**返工**都算浪費 |

> 🔑 **技術債（Technical Debt）** 雖然沒有獨立列在七種裡，但本質上是**用犧牲品質換取短期速度**，屬於「缺陷」類浪費的延伸——為了趕死線走捷徑，之後一定要花更多時間償還，這正是「浪費」的定義：消耗資源但不創造淨值。

## ⚠️ 最容易和「浪費」搞混的兩種東西：不確定性 ≠ 浪費

> **浪費**是「本來可以避免、不該存在」的資源消耗；**不確定性／估算誤差**是專案**本質固有**的風險，不是流程沒做好。

| 情境                     | 是浪費嗎？             | 為什麼                                                   |
| ---------------------- | ----------------- | ----------------------------------------------------- |
| **預算超支，因為最初成本估算不準**    | ❌ **不是浪費**        | 估算本身有不確定性是專案的**本質**，不是「多消耗了不該消耗的資源」——這是風險／估算議題，不是精實浪費 |
| **排程延誤，因為出現未預期的技術複雜度** | ❌ **不是浪費**        | 技術複雜度是**固有的不確定性**，事先不知道、不是流程缺陷造成的延誤                   |
| **等三天才拿到架構師的技術答覆**     | ✅ **是浪費**（Delays） | 這不是「複雜度」造成的，是**流程／溝通機制**的問題（響應太慢），本可避免                |

> 🔑 判準：**這個延誤／超支是「本來可以更快、不該發生」，還是「本質上就有不確定性、算不準也正常」？**
> 前者是浪費（流程問題，可改善）；後者是風險（本質問題，靠風險管理處理，不是精實原則要解決的對象）。

## 判斷口訣

> 症狀是「**等待、過度審批、多餘文件、交接**」→ **Eliminate Waste**（症狀本身就是浪費的定義）。
> 症狀是「**太早鎖定方案、缺乏彈性**」→ Defer Commitment。
> 症狀是「**交付週期太長，想加速**」（且不是因為浪費）→ Deliver Fast。
> 症狀是「**品質靠事後檢驗、常常返工**」→ Build Quality In。
> 多選題判斷「這是不是浪費」時：**能否避免、是不是流程問題** → 是浪費；**本質不確定性、估算誤差** → 不是浪費，是風險。
