## ➕ 新增（10/18）

### Skills/dating-budget-report/ — 約會帳本分析 + PDF 月報

**做了什麼：**
- 新增 `Skills/dating-budget-report/`：把約會記帳 App 匯出的分帳 CSV，轉成月度分類分析 Excel，再轉成給女朋友看的視覺化 PDF 月報
  - `build_excel.py`：解析原始「付款者/應分攤」兩列一組結構 → 取總金額（不管誰付、怎麼分攤）→ 偵測代墊款（非對半分攤的全額歸一人）→ 跟舊 Excel 明細合併（保留使用者手動修正過的分類，含自訂新類別如「瑟瑟」）→ 輸出 Excel
  - `build_pdf.py`：讀 Excel 明細 → 內部暫時渲染 html（不留檔）→ 用 headless Edge 實測每月真實內容高度 → 轉成逐月剛好貼合的 PDF 頁 → 合併成一份多頁 PDF
  - `category_rules.py` / `photo_map.json` / `photos/`：分類關鍵字規則、已知類別顏色/emoji、「本月最大一筆」對應的真實地點/店家照片（已查證來源，壓縮至 100KB 內）
- 輸出位置獨立成 `Desktop/約會記帳/`（含 `原始匯出/` 存檔歷次 CSV），刻意跟 `家庭記帳/`（富邦帳單）分開
- 更新 `Skills/skills-index.md` 加入索引

**推論：**

1. **這是第三條獨立的記帳線，不能跟既有的混在一起。** Vault 裡已經有 `家庭記帳/bill_grab.py`（富邦銀行帳單）跟 `Skills/budget-import`（Budget App 一般記帳），但約會開銷的資料結構（雙人分帳、應分攤邏輯）跟用途（產出給女朋友看的報告，不是自己內部記帳）完全不同，混在同一個資料夾會讓邏輯互相污染。

2. **「代墊款」是這份資料特有的陷阱，必須用演算法偵測，不能硬編碼清單。** 原始分帳 App 的「應分攤」欄位裡，有 6 筆金額全額算在單一人頭上（不是真的對半分攤），本質是個人代墊/欠款，不是共同開銷。這點是從實際資料回溯發現的，不是一開始就知道——所以 `build_excel.py` 直接比對原始兩欄金額來判斷，而不是記錄「這 6 筆是代墊」這種會隨新資料失效的清單。

3. **分類合併邏輯以使用者手動修正為準，不是以程式規則為準。** 使用者在 Excel「明細」分頁手動改過的分類（包含自創類別「瑟瑟」）代表真實意圖，比關鍵字規則準。所以重跑 `build_excel.py` 時用 (月份,項目描述,金額) 回頭比對舊明細，舊分類永遠優先，新交易才套用規則分類——這樣才能安全地重複執行，不會每次都把人工修正洗掉。

4. **最終只要 PDF，html 跟分檔案的版本都是走過的彎路。** 一開始做了「每月一份 html + 上一月/下一月連結」，結果女朋友端打不開 html、而且相對路徑連結在只傳單檔時會失效；改成「合併單檔 html + JS 切換」解決了路徑問題，但對方仍不方便開 html。最後確認她只需要 PDF（手機原生就能滑動翻頁），所以把 html 降級成 `build_pdf.py` 內部用完即刪的中間產物，不再是獨立交付物——這也是為什麼最終版的 Skill 資料夾裡沒有任何 html 檔案。
