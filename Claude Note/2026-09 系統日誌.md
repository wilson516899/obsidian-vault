### Projects/PMP/ — PMP 備考主計畫

**做了什麼：**

  - 考期由「2026 年 9 月」改為「約考 12/13 / 截止線 12/31」
  - 費用 544 USD 更正（PMI 於 2026/8/6 調漲：非會員 675 / 會員 445）
  - Q2 KR 摺疊保留並標記未完成原因，新增 Q4 KR

**推論：**

1. **考試已改版是整件事的前提。** 2026/7/9 起 PMP 換新版 ECO，Business Environment 由 8% → 26%，PMBOK 已出第八版（2025/11）。Wilson 讀的第六版落後兩個世代，原計畫的行動項全部失效。不先確認這件事，後續所有規劃都會建立在錯誤前提上。

2. **真正的卡點不是知識，是 35 contact hours。** 自讀 PMBOK 不計入 contact hours，而它是報名硬門檻。Q2 KR3 至今未完成 —— 這是原訂 9 月考期跳票的真正根因。計畫因此把「報名課程繳費」定為唯一的下一步行動，而非任何讀書任務。

3. **計畫刻意設計成對抗過度準備。** 依 CLAUDE.md 的思維模型，Wilson 的風險是「分析 > 行動、把準備當成進度」。本次跳票正是該模式的實證（讀了 700 頁參考書，卻沒完成報名門檻）。因此：
   - 出考場判準寫成硬數字（連續 3 次 ≥ 75%），定位為**終點線而非待優化參數**
   - 加入「不再新增學習資源」「考試日期先於準備程度」等護欄
   - 要求「申請一核准就立刻約考」，用已付費的日期反推準備

4. **節奏設計預留失敗空間。** 平日規劃 4 天而非 5 天（第 5 天當補課日）、設 25 分鐘下限而非只設 90 分鐘目標 —— 對容易因斷鏈而自我否定的人格，讓計畫預先容納失敗比追求全勤更穩。

5. **方法論綁定既有技能以降低啟動阻力。** 將錯題本設計為 4 行結構並要求每兩週做 EDA，把備考轉譯成 Wilson 的本職工作（數據分析）語言，同時解決「錯題本寫成長篇心得而無法統計」的常見失敗。

### 補產 9/8、9/9 Daily Note

**做了什麼：**
- 以 `TARGET_DATE=2026-09-08`、`TARGET_DATE=2026-09-09` 依序執行 `notify.py`

**根因：WSL 未在排程時間運行。**

**待觀察：** README 記載「Windows 啟動時自動觸發」，但實際未在 8:00 前喚起 WSL。若後續仍反覆漏跑，需檢討觸發方式（例如改用 Windows 工作排程器喚起 WSL，或改為開機後補跑而非固定時刻）。

## 🐛 修正（9/9）

### quest.py：連擊永遠為 1、且重跑會重複計分

**改了什麼：**
- **Bug 1 — streak 邏輯**（連擊區塊）：新增 `prev_day`，改為與「YESTERDAY 的前一天」比對
  ```python
  # 修正前：if last == YESTERDAY  → 結構上永不成立
  # 修正後：
  prev_day = (datetime.strptime(YESTERDAY, "%Y-%m-%d") - timedelta(days=1)).strftime("%Y-%m-%d")
  if last == prev_day:
      progress["streak"] = progress.get("streak", 0) + 1
  else:
      progress["streak"] = 1
  ```
  同時移除已被新防呆取代的 `elif last == TODAY: return`
- **Bug 2 — 冪等防呆**：在 `load_progress()` 之後、任何寫入之前加入
  ```python
  if any(e.get("date") == YESTERDAY for e in progress.get("daily_log", [])):
      print(f"{YESTERDAY} 已結算過，跳過（避免重複計分）")
      return
  ```
- 備份：`/tmp/quest.py.bak`（Git Bash /tmp，即 Windows 暫存）

**推論：**

1. **Bug 1 根因是狀態語意錯置。** L309 把 `last_updated` 寫成「已結算日（YESTERDAY）」，但連擊判斷卻拿它跟 `YESTERDAY` 比。每日正常執行時 `YESTERDAY` 會往前推進一天，於是 `last_updated` 恆等於 `YESTERDAY - 1`，`if last == YESTERDAY` **結構上不可能成立**，每天都落入 `else` 把 streak 重設為 1。資料佐證：09-02～09-05 為連續得分日，`streak` 全為 1。影響是 `streak_bonus = min(streak*2, 30)` 永遠只給 +2，上限 30 從未觸及 —— 系統長期低估積分。

2. **兩個 bug 是同一處程式碼的一體兩面。** `last == YESTERDAY` 唯一會成立的情境，正是「同一日期重跑」；此時它不但不擋，反而 `streak += 1` 並再次累加積分。亦即該防呆是反的：**該擋的重複執行放行，該累計的正常流程重設**。因此兩者必須一併修，只修其一會留下矛盾。

3. **採「只修往後、歷史不動」（使用者決策）。** 回溯重算 118 天雖然數字最正確，但會讓積分明顯膨脹、很可能立即憑空觸發 700 pt 的衣著採購獎勵。積分系統的價值在於行為回饋的可信度，靠補算換來的獎勵會破壞這層信任。故歷史保留原樣，自 9/9 結算起 streak 正確累計。

4. **驗證方式刻意分兩種，避免污染真實資料。**
   - Bug 2：直接對真實資料重跑已結算的 9/8 → 輸出「已結算過，跳過」，`total_pts` 680→680、`daily_log` 120→120 筆，零變動
   - Bug 1：另建隔離沙箱 `/tmp/questsb`（WSL 內，非 Git Bash /tmp）模擬 9/10 結算 9/9 → 得「連擊 2 天、加成 +4」，確認可正常累進；測畢刪除沙箱，真實 `progress.json` 維持 680 / streak 1 / last_updated 2026-09-08

## 🧮 補結算（9/9）

### 9/7、9/8 積分結算

**做了什麼：**
- 備份 `progress.json` → `/tmp/progress.json.bak-20260909-212251`
- 依序執行 `TARGET_DATE=2026-09-08`（結算 9/7）、`TARGET_DATE=2026-09-09`（結算 9/8）

| 日期 | 完成任務 | 基礎 | 連擊 | 當日 |
|---|---|---|---|---|
| 9/7（二） | 體重 75.0、PMP 45 分、飯後走路 | 45 | +2 | **+47** |
| 9/8（三） | 體重 75.5、運動課出席、PMP 30 分 | 40 | +2 | **+42** |

- 累計 591 → **680 pt**（距衣著採購 700 pt 剩 20 pt）；PMP 累計 270 分鐘
- 驗證 `daily_log` 中 9/7、9/8 各僅 1 筆，無重複

**推論：**

- **逐日執行並逐次驗證，而非一次跑完。** 修正前的 quest.py 不具冪等性，重跑會重複計分；在防呆補上之前，只能靠「一次一天、跑完立刻核對出現次數」來保證正確。此順序不可調換。
- **9/9 不補結算。** quest.py 的語意是「結算昨日」，9/9 應由 9/10 的排程處理。若此刻以 `TARGET_DATE=2026-09-10` 強行補，`last_updated` 會提前寫成 9/9，明日 cron 再跑就會落入 Bug 2 的重複計分路徑。修正後雖已有防呆，仍維持原設計語意，不提前結算當日。

### PMP 錯題本 → 知識庫系統

**做了什麼：**
- 新增 `Projects/PMP/錯題本.md`（索引用）與 `Projects/PMP/知識庫/`：`_索引.md`、Tuckman 團隊發展階段、衝突處理與升級階梯、開發方法與生命週期、範疇蔓延與鍍金
- 錯題 E001–E004 建檔，Clipping 皆加回連
- `CLAUDE.md`：按需讀取規則新增第 7 條（PMP 只掃 `Projects/PMP/`）、第 8 條補上「含 `grep -r .` 全域搜尋」；新增「PMP 錯題處理流程」章節

**推論：**

1. **錯題本定位為索引而非讀物。** 使用者要的最終產物是「由錯題長出來的知識庫」，複習時看知識庫、不回頭讀錯題。故錯題本每則壓到 5 行並指向知識點，知識密度集中在 `知識庫/`。

2. **移除錯題分布統計（使用者 9/9 決策）。** 原設計以封閉標籤詞彙表支撐錯型分佈分析；使用者判斷自己底子不足、目的是靠刷題補框架而非診斷弱項，統計對他無決策價值。標籤詞彙表的唯一用途是餵統計，故一併移除。

3. **改用 PMBOK 8 分類標註。** 需先確認真實架構：PMBOK 8 為 6 原則 / 7 績效領域（Governance、Scope、Schedule、Finance、Stakeholders、Resources、Risk）/ 5 Focus Areas 共 40 流程，與第七版差異極大（第七版的 Team、Development Approach 等領域已不存在）。完整地圖存於 `知識庫/_索引.md` 供核對，避免日後憑印象標錯。

4. **全域 grep 是既有規則的違反，非規則缺漏。** 建立 E001–E004 期間對整個 Vault（453 個 .md）執行了三次 `grep -ril`，牴觸原第 7 條「不要一次掃整個 Vault」。原條文只寫「讀取」，未涵蓋搜尋，故實務上被略過。此次明確把全域搜尋納入該條，並補上 PMP 專屬的範圍限縮條款——PMP 知識結構上只會存在於 `Projects/PMP/`，掃全 Vault 除浪費外還會產生偽陽性（E003 曾誤中 `圖書館/CLEC寶典.md` 的「生命週期投資法」，多耗一次工具呼叫排除）。

5. **流程寫進 CLAUDE.md 而非僅存於對話。** 此工作流會長期重複（使用者持續貼 Clipping 連結），且回覆格式已由使用者明確規範（只給表格、不展開講解）。寫入 CLAUDE.md 才能跨 session 生效。

## ➕ 新增（9/24）

### Projects/PMP/複習路線圖.md —— 錯題診斷與複習方向

**做了什麼：**
- 新增 `Projects/PMP/複習路線圖.md`，成為 PMP 的第三個入口（主計畫＝怎麼讀／錯題本＋知識庫＝複習什麼／路線圖＝往哪走）
- 內容：E001–E037 的質化診斷、五個失分模式（含錯題編號可回溯）、三軸複習大綱、盲區警訊、刷題方法判定、題庫版本風險
- `PMP 備考主計畫.md` 錯題本區塊加上路線圖連結
- 本日另建 E031–E037 七則錯題與 4 份新知識點（JIT、Scrum 四大儀式、管理與激勵理論、XP 實踐），並擴充 WBS（補 OBS/RBS/RAM 辨析）、僕人式領導（補跨框架角色對照）、EVM（補文件流向）

**推論：**

1. **這不是 9/9 被取消的「錯型分佈統計」，前提已經改變。** 9/9 移除統計的理由是「使用者底子不足、目的是靠刷題補框架，統計無決策價值」。但 37 則錯題累積後的實際發現是**相反的**——89% 的錯誤中，使用者選的都是真實存在的 PM 概念（只有 11% 是真知識缺口）。這推翻了「底子不足」的前提，也因此讓診斷第一次具備決策價值：它直接否定了「繼續讀更多」這條路。故本次採**一次性質化診斷**（看錯誤的結構），而非被取消的機械式標籤計數，兩者性質不同。

2. **診斷結果獨立於選擇偏差，但結論方向不獨立。** 分析素材只有錯題，無法得知正確率、蒙對題、強項。但「錯誤的結構」（層級錯置、偏向積極選項、干擾項全真）是看錯誤長什麼樣，不受錯誤率影響，故成立；盲區推論（Risk 6 流程僅 1 錯）也來自流程基數與答題進度，非來自錯題本身。已在文件開頭明確標註資料限制，避免日後誤當能力評估。

3. **複習大綱刻意不照 7 大績效領域編排。** 錯誤不是均勻分散在領域裡，而是集中在近義概念的辨析上（Portfolio/Program、Manage QA/Validate Scope、PERT/CPM/PDM、Theory Y/Z）。照領域複習會把同一個辨析點拆散到不同章節；照「辨析軸／順序鏈／計算」三軸編排才對得上實際失分結構。

4. **獨立成檔而非併入主計畫。** 主計畫是**方法論與時程**（怎麼讀、讀多久、何時報名），路線圖是**由實證資料產生的診斷**（往哪走），後者會隨錯題累積而更新、前者不會。混在一起會讓主計畫持續膨脹並模糊定位。

5. **主計畫的過期段落未擅自刪除。** 「把錯題本當 dataset／每兩週跑錯題統計」與 9/9 決策衝突，已在路線圖末尾標為待辦並說明衝突點，留待使用者確認後再清理——單方面刪除使用者主計畫的內容風險高於留下標記。
